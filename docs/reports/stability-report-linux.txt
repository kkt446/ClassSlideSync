课件续页（ClassSlideSync.Plugin 1.2.2.0）Linux 可加载性改造报告
================================================================

日期：2026-10-31
范围：只改「能不能在 Linux 上装/加载/不崩」和「明确告知本平台不可用」；Windows 侧功能一行不减。
版本号 manifest.yml: 仍是 1.2.2.0（未动）；supportedOSPlatforms: 仍是 [Windows]（未动）。

结论（先说答案）
----------------------------------------------------------------
1. 插件 dll 现在是纯 net8.0：deps.json 只列 Microsoft.NETCore.App / .NETCoreApp,Version=v8.0，
   没有 WindowsDesktop、没有 net8.0-windows、没有 WinRT 引用 —— 这是「Linux 上 Assembly.LoadFrom
   能过」的硬条件。
2. Linux 上 Plugin.Initialize 第一行就分流：只写一行日志、注册一个只读设置页（标题「课件续页」，
   正文「本插件依赖 Windows 的窗口与 COM 自动化，当前平台不可用」），然后 return。
   卡片/组件/行动/规则/触发器/教程一个都不注册，SlideSyncService 根本不会 new，
   NativeOverlayCard / PptBridge / TrayNotifier 连构造都不会发生。
3. 四个 Windows 专属入口另加了 16 处运行时护栏（OperatingSystem.IsWindows 派生的
   PlatformGuard.IsWindows）。就算有人绕过闸门直接调 Arm / Step / Show / Start，也只是记一行
   `platform: skipped (non-windows) <what>` 然后返回，不抛。
4. Windows 侧：所有护栏都是 `if (!IsWindows) { …; return; }` 的提前返回，Windows 上
   PlatformGuard.IsWindows 恒为 true ⇒ 这些 return 不可达，函数体后半段与改动前逐行相同。
5. 构建与打包：Rebuild 0 error；`-p:CreateCipx=true` 打包成功（14 项，含 ToastHelper）。
   模拟 Linux（$(OS)=Unix、输出目录无 ToastHelper）打包也 0 error、7 项、无 ToastHelper。
6. 离屏断言 120 条全绿（0 失败）。
7. 边界：没有 Linux 实机、没有 WSL，所以「Linux 上真的能装/能显示」属于静态+结构证据，
   不是在 Linux 桌面上跑出来的结论，详见最后一节。

一、TFM 改动
----------------------------------------------------------------
文件：ClassSlideSync.Plugin/ClassSlideSync.Plugin.csproj

  - <TargetFramework>net8.0-windows</TargetFramework>
  + <TargetFramework>net8.0</TargetFramework>

改完后的客观证据（bin/Release/net8.0）：
  - ClassSlideSync.Plugin.runtimeconfig.json:
      "tfm": "net8.0"
      "framework": { "name": "Microsoft.NETCore.App", "version": "8.0.0" }
  - ClassSlideSync.Plugin.deps.json:
      "name": ".NETCoreApp,Version=v8.0"
      全文无 WindowsDesktop / net8.0-windows / WinRT / Microsoft.Windows 字样
  - 输出目录里没有 Avalonia/ClassIsland 的 dll：它们由宿主进程提供（与原设计一致）。

没有用编译期开关：全仓 .cs 里没有一行 `#if WINDOWS` 预处理指令
（Core/PlatformGuard.cs 的注释里提到过这个词，被断言按「注释不算」处理）。
两端拿到的是同一个二进制，判断全在运行时。

CA1416（调用 Windows 专属 API）没有用 pragma 压：新增的
[SupportedOSPlatformGuard("windows")] PlatformGuard.IsWindows 让 Roslyn 把
`if (!PlatformGuard.IsWindows) { …; return; }` 认成平台分支，后面的 COM/user32 调用自动不再告警。
Build 里 CA1416 数量：0。

二、新增文件
----------------------------------------------------------------
1) Core/PlatformGuard.cs（新，81 行）
   - `[SupportedOSPlatformGuard("windows")] public static bool IsWindows => OperatingSystem.IsWindows();`
     （第 33-37 行）—— 属性而不是缓存字段，每次实时查询；IL 里直接 call
     System.OperatingSystem::IsWindows()（断言用 IL token 解析验证过）。
   - `public static void Announce(string what, Action<string>? log = null)`（第 50 行）
     固定文案 `platform: skipped (non-windows) <what>`（第 61 行），同一个 what 只记一次
     （HashSet + lock），log 为 null 退回 stderr；Windows 上不会被调用。
   - ResetAnnouncements() / AnnouncementCount 仅测试用。

2) Views/SettingsPages/PlatformUnavailablePage.cs（新）
   - `[SettingsPageInfo("classslidesync.unavailable", "课件续页", "\uE7C3", "\uE7C3")]`
   - `public sealed class PlatformUnavailablePage : SettingsPageBase`，无参构造，不用 XAML：
     StackPanel(Spacing=12, Margin=24) 里两个 TextBlock：
       标题「课件续页」(FontSize=22, SemiBold)
       正文「本插件依赖 Windows 的窗口与 COM 自动化，当前平台不可用。」(TextWrapping=Wrap)
   - 页面里没有任何可交互控件，「只读」是字面意思。

三、平台闸门（要求 3）
----------------------------------------------------------------
文件：Plugin.cs:47-56

    if (!OperatingSystem.IsWindows())
    {
        new Ledger(PluginConfigFolder).Log(
            "platform: non-windows — only the read-only settings page is registered; " +
            "cards / components / automations / triggers / tutorial are skipped");
        services.AddSettingsPage<PlatformUnavailablePage>();
        return;

- 位置：Initialize 的第一条语句之前（DataFolder / LoadConfig / new SlideSyncService 全在它后面）。
- 闸门里刻意不调 PlatformGuard.Announce：闸门不是「跳过」，Linux 上这就是唯一会走的路，
  所以文案写清楚「只注册了只读设置页」。
- Windows 上这个分支恒不成立，第 58 行之后与改动前完全一致。

五、Linux 上到底会执行到什么（调用链）
----------------------------------------------------------------
宿主（ClassIsland Linux）加载插件 dll
  → 反射找到 [PluginEntrance] ClassSlideSync.Plugin.Plugin
  → new Plugin()（只跑字段初始化，无 IO、无窗口）
  → Plugin.Initialize(context, services)
      → Plugin.cs:47  OperatingSystem.IsWindows() == false
      → Plugin.cs:51  new Ledger(PluginConfigFolder).Log("platform: non-windows — ...")
           （Ledger.Log 内部 CreateDirectory + try/catch，目录不可写也不会抛）
      → Plugin.cs:55  services.AddSettingsPage<PlatformUnavailablePage>()
           （读 [SettingsPageInfo]，登记 SettingsWindowRegistryService.Registered，
             注册 keyed transient <SettingsPageBase, PlatformUnavailablePage>）
      → Plugin.cs:56  return
  → 宿主继续启动；设置窗打开时按 id `classslidesync.unavailable` 解析该页面
      → PlatformUnavailablePage 构造：new StackPanel + 2×TextBlock，Content=panel
  → 之后：没有 AppStarted/AppStopping 订阅、没有 SlideSyncService、没有 Ledger 轮询、
    没有 NativeOverlayCard / PptBridge / TrayNotifier 实例、没有 COM、没有 user32 窗口、
    没有 ToastHelper 子进程。

即：Linux 上的插件「装上→被识别→设置里看到一个说明页→不崩」，没有任何一条代码路径会碰 Windows API。

六、Windows 上为什么零回退（证据）
----------------------------------------------------------------
1) 闸门与护栏的判据是运行时真值，不是常量：断言解析了 PlatformGuard.get_IsWindows 的 IL，
   确认里面是对 System.OperatingSystem::IsWindows() 的 call，且类里没有缓存 bool 字段。
   本机 Windows 上 IsWindows == true ⇒ 第三节的闸门不成立、16 处护栏的 return 全部不可达。
2) 闸门之后（Plugin.cs:58-134）与改动前逐行相同：
   LoadConfig(SyncSettings.json)、new SlideSyncService、ToastNotifier.InstallOnce、
   AddSingleton(Settings/Service)、AddSettingsPage<SlideSyncSettingsPage>()、
   8 个 AddAction（OpenUnfinishedDeck / ToggleCard / Notify / OpenPanel / JumpLastPage /
   JumpToPage / OpenDeckFolder / ClearDeckHistory）、AddRule(UnfinishedDeckRule)、
   AddTrigger(SlidePageReached)、AddComponent(DeckProgressComponent)、TutorialGuide.Register()、
   AppStarted→Service.Start()、AppStopping→Service.Stop()。
3) 功能源码未删：PptBridge 11 处 DllImport + [ComImport] 接口、NativeOverlayCard 50 处
   DllImport（分层窗口/GDI/消息循环）、TrayNotifier 的 Shell_NotifyIconW 全部在位。
4) 纯函数回归断言（TFM 切换不改逻辑）：
   PptBridge.LooksLikePath(路径/非路径)、NativeOverlayCard.ProgressRatio(5,10)=0.5、
   ProgressFillWidth(100,3,10)>0 等全部通过。
5) 版本与清单：
   - manifest.yml: version: 1.2.2.0（未动）
   - manifest.yml: supportedOSPlatforms: [Windows]（未动，市场里 Linux 会标灰）
   - Assembly.LoadFrom 加载的仍是同一个 ClassSlideSync.Plugin.dll（1 个二进制两端通用）
6) 构建：`dotnet build ClassSlideSync.Plugin.csproj -c Release -t:Rebuild --nologo`
   → 0 error，218 warning（全是改动前就有的 CS860x/CS0414/CS8618 与 2 条 AVLN3001，
   与本次改动无关；CA1416 = 0）。

九、未验证的边界（必读）
----------------------------------------------------------------
1) **没有 Linux 实机验证。** 这台机器没装 WSL（`wsl --status` 返回「未安装用于 Linux 的
   Windows 子系统」），也没有 Linux 桌面。所以「Linux 上能装、能加载、不崩」的依据是：
   - TFM/依赖层面：dll 是 net8.0，runtimeconfig/deps 只依赖 Microsoft.NETCore.App；
   - 代码层面：Initialize 第一行分流 + 16 处提前返回，静态与 IL 断言覆盖；
   - Windows 上同一份 dll 的完整加载、反射调用、离屏渲染都通过（证明程序集自洽）。
   真机验证仍需：在 Linux 桌面装 ClassIsland 2.x → 安装 cipx → 看插件列表出现「课件续页」
   → 打开设置看到说明页 → 不崩。这一步没做。
2) OS=Unix 打包是 MSBuild 属性模拟，不是真 Linux dotnet。真实 Linux 上：
   $(OS)=Unix，两个 ToastHelper target 会跳过（条件已在断言里固定）；但 Linux SDK 的
   path/zip 行为未实测（CreateCipx 用 ZipDirectory，理论无平台差异）。
3) 宿主侧风险不在本插件控制范围：ClassIsland 的 Linux 平台是否会在 Initialize 之外调用
   插件的其它入口（例如组件/行动的反射构造）。我们已保证这些类型在 Linux 上不会被注册，
   但如果宿主强行扫描程序集并对每个类型做 Activator.CreateInstance，仍可能构造
   NativeOverlayCard（它的构造函数已加护栏，不会抛）或带参类型（无参构造不存在，会抛异常，
   那是宿主行为）。这一点无法在没有 Linux 实机的情况下证否。
4) 设置页离屏渲染的字体来自本机；页面内容已用 TextBlock.Text 断言逐字校验，截图仅作辅证
   （随报告存档：ClassSlideSync.Plugin/stability-linux-page-render.png；每次运行为 %TEMP%\slidesync-stability\linux-run-<时间戳>\platform-unavailable-page.png），字形栅格化在裸 Application 下
   与宿主主题字体不完全一致，不代表页面在 ClassIsland 里的最终外观。
5) 未部署、未动 git、未加任何 NuGet 包；主工程依赖仍是原来的 ClassIsland.PluginSdk 2.1.0.1。
