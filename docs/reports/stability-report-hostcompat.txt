课件续页（ClassSlideSync.Plugin 1.2.2.0）宿主兼容（ClassIsland 2.0.x ~ 2.1.x）改造报告
================================================================

日期：2026-10-31
范围：让插件在 ClassIsland 2.0.0.1 ~ 2.1.0.1 全部 2.x 宿主上「能加载、能跑基础功能」；
      2.1 才有的能力在旧宿主上降级（缺功能可以，但不能崩、不能白屏、不能静默）。
版本号 manifest.yml：仍是 1.2.2.0（未动）；TFM 仍是 net8.0（未动）；manifest.yml / SyncSettings /
Views / ControlPanel / *.csproj 一行未改。改动的只有 Plugin.cs 和新增的 Core/HostCompat.cs。

结论（先说答案）
----------------------------------------------------------------
1. 「2.1 才有的 API」这个前提基本不成立。把 nuget 上 ClassIsland.Core 六份真实包
   （2.0.0.1 / 2.0.1 / 2.0.2 / 2.0.3 / 2.0.4 / 2.1.0.1）逐条反射核对 56 项后：
   ActionBase / TriggerBase / ComponentBase / SettingsPageBase / TriggerSettingsControlBase<T> /
   AddAction<T> / AddAction<T,TSettingsControl> / AddTrigger<T> / AddTrigger<T,TSettingsControl> /
   AddComponent<T> / AddRule / AddSettingsPage<T> / 四个 [*Info] 特性 / AppBase / ILessonsService /
   IUriNavigationService / IAppHost / ConfigureFileHelper —— 从 2.0.0.1 起就全部存在。
   我们真正用到、而 2.0.x 里会缺的只有一样：教程系统（ITutorialService + TutorialGroup，
   2.0.3 才加）。
2. 2.0.4（本报告的基准版本）缺什么：我们用的宿主 API **一个都不缺**；唯一「无」的是
   SettingsPageCategory.Plugins 这个枚举成员 —— 它在包括 2.1.0.1 在内的所有版本里都不存在，
   而我们的 [SettingsPageInfo] 走的是 5 参 ctor，默认值取自枚举里已存在的成员，因此不构成风险。
3. 因此降级面很小但逻辑仍然保留：旧宿主（2.0.0.1~2.0.2）缺教程系统 → 只跳过「新手引导」一节，
   记一行 `compat: skipped tutorial (host <ver> lacks ITutorialService.RegisteredTutorialGroups)`；
   2.0.0.1 还缺 AddSettingsPageGroup(id,icon,name) 三参重载 —— 我们没用到，仅记录在案。
   其余行动 / 规则 / 触发器 / 组件 / 设置页在 2.0.0.1 上照常注册。
4. 改造方式：注册之前先反射探测宿主能力（Core/HostCompat.cs），每个注册分区包在
   TryRun/Skip 里；缺失时跳过并记一行，同一 feature 只记一次；注册体自己抛异常也吞掉并记
   `compat: failed ...`，绝不把异常抛给宿主（Initialize 抛异常 = 插件加载失败 = 白屏）。
   2.1 宿主上能注册的项目与改造前逐项相同，没有为了兼容砍功能。
5. 构建：Rebuild 0 error / 218 warning（全是改动前就有的 nullable 警告）；
   `-p:CreateCipx=true` 打包成功（cipx 14 项、6,719,122 字节，含 manifest.yml 与插件 dll）。
6. 离屏断言 149 条全绿（A 108 + B 22 + C 19），0 失败；全程无窗口、无 Start-Process、
   不启动 ClassIsland / WPS / 希沃。

为什么必须「先探测再调用」，而不是 try/catch 包住调用点
----------------------------------------------------------------
插件是按 2.1.0.1 的 SDK 编的，IL 里写死了 2.1 程序集里的类型/成员引用。CLR 在**方法开始执行
之前**就解析该方法体用到的类型 token：宿主缺类型时抛的是 TypeLoadException，方法自己的
try/catch 还没机会运行 —— 这就是「在旧宿主上一点就白屏」的机理。
所以判断必须在调用点**之前**、用反射完成：反射查的是名字字符串，不需要类型存在。
HostCompat 的全部实现（含探测与日志）都是这个形状，且不引用任何 ClassIsland/Avalonia 类型。

验证方法（可复现，全部离屏）
----------------------------------------------------------------
- 包来源：nuget.org 的 ClassIsland.Core / ClassIsland.Shared / ClassIsland.Shared.IPC
  2.0.0.1 / 2.0.1 / 2.0.2 / 2.0.3 / 2.0.4，解包到 %TEMP%\ci204\classisland.core.<ver>（2.0.4 在
  %TEMP%\ci204\core）；2.1.0.1 取本机 nuget 缓存。没有 dotnet add package、没有引用进工程。
- 反射探针：%TEMP%\ci204\probe（net8.0 控制台，AssemblyLoadContext 解析依赖），
  对每份 ClassIsland.Core.dll 跑同一份 56 项清单，结果落 %TEMP%\ci204\facts-<ver>.txt。
- 能力层单测：%TEMP%\ci204\compat-tests，直接链接工程里的 Core/HostCompat.cs 源文件
  （测的就是生产代码，不是副本），把六份真实 Core 各装进独立 ALC 探测；再用假探测面覆盖
  「探测抛异常 / Sink 抛异常 / 无版本号」等极端情况。
- 注册逻辑单测：同一 harness 用 AssemblyLoadContext.Default.LoadFromAssemblyPath 加载真实
  插件 dll + 真实 2.1.0.1 宿主，反射调 Plugin.RegisterAutomation(IServiceCollection, caps)，

日志格式固定为：

七、残余风险（反射查不到、必须如实记录）
----------------------------------------------------------------
1. Avalonia 版本：插件按 SDK 2.1.0.1 编译，deps.json 里 Avalonia 11.3.17；宿主实际版本
   2.0.0.1=11.3.6、2.0.1~2.0.4=11.3.10、2.1.0.1=11.3.17。.NET Core 在同一 ALC 内按简单名
   绑定，所以插件会跑到宿主的 Avalonia 上；但如果编译后的 XAML/代码用到 11.3.10 之后才加的
   Avalonia 成员，旧宿主会在运行时 MissingMethodException。本次未逐条核对 Avalonia API 差集
   （超出「宿主 API」范围），列为已知残余风险。
2. 插件 dll 的 deps.json 列出 ClassIsland.Core 2.1.0.1 / Shared 2.1.0.1。ClassIsland 把插件
   装进与宿主共享的加载上下文，按简单名命中已加载的 2.0.x 程序集，因此能加载；若某个宿主
   改成严格按版本绑定，会变成「插件加载失败」而不是「功能缺失」。这是宿主加载器行为，插件侧
   无法控制（且改 deps.json 需要改 csproj，本次不允许）。
3. 2.1.1.x 的 ClassIsland.Core 只带 lib/net10.0（宿主跑 .NET 10）。net8.0 插件在 .NET 10 宿主
   上仍可加载，但没有实测（本机没有 .NET 10 运行时跑反射探针），矩阵未覆盖 2.1.1.x。
4. 本报告的「有/无」是反射层面的静态事实；「2.0.4 上能跑」= API 层面不缺 + 注册逻辑对缺失项
   有降级。真实宿主内的行为（例如宿主对组件容器的二次校验）未在本机启动 ClassIsland 验证
   （按要求全程离屏）。
